Теория: что такое промисы

Состояние и результат

Промис - это, как и многое в JavaScript, просто объект. Просто объект со своими особенностями и нюансами. Вся магия промисов на самом деле не такая уж магия, если разобраться из чего они состоят.

У промиса как объекта есть два внутренних слота?Внутренние слоты (internal slots) — служебные поля объекта, которые недоступны из кода напрямую. Они обозначаются двойными квадратными скобками [[...]] и используются движком JavaScript для внутренней логики. или простым языком свойства, недоступных напрямую. Они определяют всю логику промисов:

  • [[PromiseState]] хранит состояние промиса

  • [[PromiseResult]] хранит результат выполнения промиса

Состояние [[PromiseState]] может принимать строго три значения — pending, fulfilled, rejected — и от него зависит, что лежит в [[PromiseResult]]:

  1. pending

    Начальное состояние промиса:

    • [[PromiseState]] = pending

    • [[PromiseResult]] = undefined

  2. fulfilled

    Промис выполнен успешно:

    • [[PromiseState]] = fulfilled

    • [[PromiseResult]] = значение, с которым промис выполнен

  3. rejected

    Промис отклонён:

    • [[PromiseState]] = rejected

    • [[PromiseResult]] причина отклонения (обычно ошибка)

Отдельного свойства для хранения ошибки нет. Всё потому, что промис ведёт себя как конечный автомат: состояние меняется только один раз: из pending либо в fulfilled, либо в rejected. Поэтому по состоянию промиса легко понять, что лежит в [[PromiseResult]]:

  • undefined если промис в pending
  • значение если в fulfilled
  • ошибка если в rejected

Со свойстами и состояними разобрались. Но кто переводит промис из pending в fulfilled или rejected? За это отвечают reject и reject — о них и поговорим дальше.

Управление состоянием промиса

Промис создается через конструктор new Promise, внутрь которого передаётся функция-исполнитель executor:

snippet(1).js
1const promise = new Promise(executor);
2
3function executor(resolve, reject) {
4  // Здесь что-то делаем
5}

Функция-исполнитель запускается синхронно, сразу же в момент создания промиса (см. статью про Event Loop). Она нужна всего для двух вещей:

  1. запустить вложенную операцию

  2. обработать её результат

Всё!

Функция-исполнитель не обязана быть асинхронной, промис может вообще и не запускать асинхронную операцию. А вот методы обработки результата, then и catch, выполняются асинхронно, через очередь микрозадач. Но до них мы ещё дойдём. В любом случае, какой бы код ни содержала функция-исполнитель, она не ждёт его выполнения— управление идёт дальше.

Чтобы обработать результат вложенной операции, когда она выполнится, в функцию-исполнитель передаётся два колбэка для управления состоянием промиса — resolve и reject:

snippet(2).js
1const promise = new Promise(executor);
2
3function executor(resolve, reject) {
4  // Здесь что-то делаем
5  // Затем resolve() и/или reject()
6}

Колбэк resolve(value) переводит промис в состояние fulfilled со значением value:

snippet(3).js
1const promise = new Promise((resolve, reject) => {
2  console.log('Этот код выполнится сразу');
3  resolve('Успешный успех');
4});

Колбэк reject(error) переводит промис в состояние rejected с причиной:error:

snippet(4).js
1const promise = new Promise((resolve, reject) => {
2  console.log('Этот код выполнится сразу');
3  reject(new Error('Ой-ой, ошибочка'));
4});

resolve и reject могут вызываться в любом месте функции-исполнителя в зависимости от логики. При этом в resolve можно передать любое значение: undefined, число, строку, булево значение, функцию, объект, массив и даже другой промис:

snippet(5).js
1new Promise((resolve) => resolve());
2new Promise((resolve) => resolve(42));
3new Promise((resolve) => resolve({ id: 42, name: 'dtsiki', isAwesome: true }));
4
5const innerPromise = new Promise((resolve) => {
6  setTimeout(() => resolve('Допустим, это сетевой запрос'), 1000);
7});
8
9new Promise((resolve) => resolve(innerPromise));

Что именно происходит, когда в resolve передают другой промис, разберём в подразделе про схлопывание.

С reject ситуация чуть отличается. Технически в него тоже можно передать любое значение — оно станет причиной отклонения. Но JavaScript не превращает его в объект Error: если передали строку, причиной будет строка; если число — число:

snippet(6).js
1new Promise((resolve, reject) => {
2  reject('Какая-то ошибка доступа');
3});
4
5new Promise((resolve, reject) => {
6  reject(404);
7});

Поэтому хорошей практикой считается передавать экземпляр класса Error — он содержит стек вызовов, что упрощает отладку:

snippet(7).js
1new Promise((resolve, reject) => {
2  reject(new Error('Что-то пошло не так'));
3})

Сработает внутри функции-исполнителя — только один колбэк: либо resolve, либо reject. Более того: сработает может только первый вызов одной из этих функций. Любые последующие вызовы resolve или reject внутри одного промиса игнорируются:

snippet(8).js
1const promise = new Promise((resolve, reject) => {
2  resolve('Успешный успех'); // Выполнится
3  reject('Ой-ой, ошибочка'); // Не выполнится
4  resolve('Снова успешный успех'); // Тоже не выполнится
5});

Если забыть вызвать resolve и reject промис может навсегда остаться в состоянии pending:

snippet(9).js
1const promise = new Promise((resolve, reject) => {
2  console.log('Этот код выполнится сразу');
3});
4
5console.log(promise);
Console
Promise {<pending>}

И сколько бы не проверяли этот промис, он всегда будет в состоянии pending.

Если resolve и reject вызываются только при определённом условии, промис тоже может зависнуть:

snippet(10).js
1const promise = new Promise((resolve, reject) => {
2  const shouldResolve = false;
3
4  if (shouldResolve) {
5    resolve('Успешный успех');
6  }
7});

Такие промисы называют висячими. С ними стоит быть осторожными: если на висячий промис остаются ссылки, он может привести к утечке памяти. А ещё — код, который ждёт результата, может так его и не дождаться.

Обработка результата выполнения промиса

Если запустить пример, который рассматривали выше, в консоли выведется только одна строка:

snippet(11).js
1const promise = new Promise((resolve, reject) => {
2  console.log('Этот код выполнится сразу');
3  resolve('Успешный успех');
4});
Console
Этот код выполнится сразу

При этом если проверить промис — он выполнился и не остался в состоянии pending:

snippet(12).js
1setTimeout(() => console.log(promise), 5000);
Console
Promise { <state>: 'fulfilled', <value>: 'Успешный успех' }

Куда же девается результат, который передали в resolve?

Вернёмся к внутренним слотам промиса. [[PromiseState]] и [[PromiseResult]] скрыты и прямого доступа к ним нет. Чтобы что-то сделать с результатом выполнения промиса, недостаточно написать что-то вроде:

snippet(13).js
1if (promise.state === 'fulfilled') {
2  // Здесь что-то делаем с результатом
3} else if (promise.state === 'rejected') {
4  // Здесь что-то делаем с ошибкой
5}

Обратите внимание: свойств state и result у промиса не существует. Это лишь иллюстрация того, что не сработает.

Для работы с результатом используются специальные методы: then и catch.

then получает результат выполнения промиса. У него есть два необязательных параметра: колбэки onFulfilled и onRejected. Обе функции принимают один аргумент — значение, которое лежит в [[PromiseResult]]. Для onFulfilled это результат, для onRejected — причина отклонения:

snippet(14).js
1promise.then(
2  (result) => {
3    // Здесь что-то делаем с результатом
4  },
5  (error) => {
6    // Здесь что-то делаем с ошибкой
7  }
8);

Часто думают, что then работает только с успешным результатом, когда промис в состоянии fulfilled. Но это не так:

index.js
1const promise = new Promise((resolve, reject) => {
2  resolve('Успешный успех!');
3});
4
5promise.then(
6  (value) => {
7    console.log(value);
8  },
9  (error) => {
10    console.error(error);
11  },
12);
Console
Успешный успех
index.js
1const promise = new Promise((resolve, reject) => {
2  reject('Ой-ой, ошибочка!');
3});
4
5promise.then(
6  (value) => {
7    console.log(value);
8  },
9  (error) => {
10    console.error(error);
11  },
12);
Console
Ой-ой, ошибочка

Как видно из примеров выше, then умеет работать и с ошибками. Для этого достаточно передать только onRejected:

snippet(15).js
1const promise = new Promise((resolve, reject) => {
2  reject('Ой-ой, ошибочка!');
3});
4
5promise.then(
6  null,
7  (error) => {
8    console.error(error);
9  },
10);
Console
Ой-ой, ошибочка!

Поздравляю! Мы только что написали метод catch!

catch — синтаксический сахар для then(null, onRejected). У него только один аргумент: onRejected, а вместо onFulfilled передаётся null.

Эти две записи делают одно и тоже:

snippet(16).js
1promise.catch((error) => {
2  console.error(error);
3});
4
5promise.then(null, (error) => {
6  console.error(error);
7});

Хоть catch и является обёрткой над then, принято для успешного результата использовать then, а для ошибок — catch:

snippet(17).js
1const promise = new Promise((resolve, reject) => {
2  throw new Error('Что-то пошло не так');
3});
4
5promise.catch((error) => {
6  console.error(error);
7});

Ещё есть метод finally. В него передаётся один колбэк onFinally, который выполнится всегда, при любом исходе промиса: fulfilled или rejected.

finally принято использовать для так называемой чистки. Например, чтобы скрыть индикатор загрузки:

snippet(18).js
1let isLoading = true;
2
3loadData()
4  .then((response) => response.json())
5  .catch((error) => console.error(error))
6  .finally(() => {
7    isLoading = false;
8  });

Технически finally не является методом обработки результата: он ничего не делает с результатом, а просто передаёт его дальше. Возвращаемое из finally значение игнорируется:

snippet(19).js
1
2const promise = new Promise((resolve, reject) => {
3  resolve(42);
4});
5
6promise
7  .finally(() => {
8    return 'You shall not pass';
9  })
10  .then((result) => console.log('Результат:', result))
11  .catch((error) => console.error('Ошибка:', error.message));
Console
Результат: 42

В этом примере, несмотря на то что из finally возвращается другое значение — строка «You shall not pass», — в then по цепочке всё равно попадает результат исходного промиса — resolve(42).

Но есть исключение: из finally можно выбросить ошибку:

snippet(20).js
1
2const promise = new Promise((resolve, reject) => {
3  resolve(42);
4});
5
6promise
7  .finally(() => {
8    throw new Error('You shall not pass');
9  })
10  .then((result) => console.log('Результат:', result))
11  .catch((error) => console.error('Ошибка:', error.message));
Console
Ошибка: You shall not pass

Резюмируем: finally, как и catch, — просто обёртки над then. Когда мы вызываем finally, под капотом вызываетсяthen с двумя колбэками: onFulfilled и onRejected. Оба колбэка вызывают onFinally, а потом пробрасывают исходное значение или ошибку дальше. Что именно происходит под капотом finally, разберём, когда будем писать этот метод в классе промиса.

Цепочка промисов

Каждый вызов then неявно создаёт и возвращает абсолютно новый промис. Как будет выглядеть этот промис зависит от того, что возвращается из колбэка прошлого then в цепочке:

  • ничего (нет return из колбэка)

    Создаётся уже выполненный промис со значением undefined

  • обычное значение: число, строка, булево значение, массив, объект

    Создаётся выполненный промис с этим значением

  • промис

    Всё равно создаётся новый промис, который будет ждать завершения того, что вернули вручную

  • ошибка, выброшенная через throw

    Создаётся уже отклонённый промис с этой ошибкой

Под капотом then делает то же самое, что и мы, когда пишем new Promise(...), — просто берёт на себя управление состоянием нового промиса.

Если внутри одного then всегда возвращается промис, а следующий then обязательно дождётся его выполнения, то таким образом можно составлять цепочки. Они так и называются — цепочки промисов.

Как это будет выглядеть:

snippet(21).js
1Promise.resolve(1)
2  .then((value) => {
3    console.log('Первый:', value);
4    return 2;
5  })
6  .then((value) => {
7    console.log('Второй:', value);
8
9    return new Promise(resolve => {
10      setTimeout(() => resolve(3), 1000);
11    });
12  })
13  .then((value) => console.log('Третий:', value));
Console
Первый: 1
Второй: 2
Третий: 3 // Через 1 секунду

Механизм, который стоит за этим поведением, называется схлопывание промисов. Его разберём отдельно —чуть позже (см. Схлопывание и развёртывание).

Очереди колбэков

Кроме уже знакомых нам [[PromiseState]] и [[PromiseResult]], у промиса есть ещё два внутренних слота для очередей колбэков:

  • [[PromiseFulfillReactions]]

    Очередь для колбэков, которые выполнятся, когда промис перейдёт в состояние fulfilled

  • [[PromiseRejectReactions]]

    Очередь для колбэков, которые выполнятся, когда промис перейдёт в состояние rejected

Именно в этих очередях колбэки ждут, пока промис завершится. А сама асинхронность уже заслуга очереди микрозадач, в которую они попадают после смены состояния (подробнее — в статье про Event Loop).

Разберём, как это работает под капотом, на примере, приближенном к реальности:

snippet(22).js
1let isLoading = true;
2
3fetch(url)
4  .then((response) => response.json())
5  .then((result) => renderResult(result))
6  .catch((error) => renderError(error))
7  .finally(() => {
8    isLoading = false
9  });

Обратите внимание

Функция fetch(url) сразу возвращает промис в состоянии pending. Когда сервер ответит, промис переходит в fulfilled и возвращает объект Response. Сам по себе Response это ещё не готовые данные, а обёртка над ними. Чтобы прочитать тело ответа, нужно вызвать специальный метод в зависимости от формата —например, json() для JSON. Этот метод тоже возвращает промис.

Поэтому в примере выше в первом then выполняется response.json(), и из него возвращается промис. Это как будто лишний шаг: then возвращает промис, но в цепочке он схлопывается с предыдущим. Подробнее — в разделе про схлопывание).

Пройдёмся пошагово и разберёмся что происходит в этом примере:

  1. Функция fetch() сразу возвращает промис (A), не дожидаясь ответа сервера. Изначальное состояние этого промиса pending.

    Каждый колбэк в цепочке будет тоже возвращать новый промис:

    snippet(23).js
    1fetch(url)                                // промис А
2  .then((response) => response.json())    // промис B
3  .then((result) => renderResult(result)) // промис C
4  .catch((error) => renderError(error))   // промис D
5  .finally(() => { isLoading = false });  // промис E

  2. У fetch() нет видимой нам функции-исполнителя — браузер делает всю работу сам. Но представим, что на этом шаге начинает выполняться executor: в Web API отправляется сетевой запрос. При этом executor не ждёт ответа — неизвестно, сколько времени займёт запрос: это может быть и миллисекунда, и минута. Поэтому executor только запускает асинхронную операцию и не ждёт её результата. Код идёт дальше, а когда сервер ответит — вызовется resolve или reject.

  3. Код продолжает выполняться. На пути цепочка промисов: два then, catch и finally. Движок не может выполнить колбэки внутри этих методов потому что первый промис (A) всё ещё в состоянии pending. Здесь на помощь приходят очереди [[PromiseFulfillReactions]] и [[PromiseRejectReactions]]: колбэки будут откладываться каждый в соответствующую очередь:

    • Колбэки из then отправятся в [[PromiseFulfillReactions]]

    • Колбэки из catch отправятся в [[PromiseRejectReactions]]

    • Колбэки из finally отправятся и в [[PromiseFulfillReactions]], и в [[PromiseRejectReactions]]

      Про это разберём отдельно в практике — в разделе про кастомный finally

    У then есть второй аргумент onRejected. Если им воспользоваться, колбэк попадёт в[[PromiseRejectReactions]] — так же, как колбэк catch, который является синтаксическим сахаром then(null, onRejected).

    Таким образом в очередях будут лежать следующие колбэки:

    • [[PromiseFulfillReactions]]: колбэки из then response.json() и renderResult(result), а также колбэк из finally

    • [[PromiseRejectReactions]]: renderError(error) и снова колбэк из finally

    Когда выполнится промис, соответствующий колбэк будет взят из очереди и выполнен. При этом каждый колбэк должен отреагировать на «свой» промис. В нашем случае будет следующая цепочка реакций и вызовов. Начнётся всё с того, что fetch() создаёт промис (А). Когда:

    • выполняется промис (A):

      если успешно: берётся колбэк первого then из очереди [[PromiseFulfillReactions]] — response.json(). Этот колбэк в свою очередь тоже создаёт промис — (B). Следующие колбэки ждут выполнения промиса (B). Когда:

      • выполняется промис (B):

        если успешно: берётся колбэк второго then из очереди [[PromiseFulfillReactions]], — renderResult(result). Здесь тоже колбэк вернёт промис, — (C), даже если из функции нет явного возврата промиса. Когда:

        • выполняется промис (C):

          если успешно: берётся колбэк finally из очереди [[PromiseFulfillReactions]]. Конец цепочки.

          если с ошибкой: выполняется колбэк из catch из очереди [[PromiseRejectReactions]]. Колбэк создаёт промис (D). Когда:

          • выполняется промис (D):

            если успешно: из очереди [[PromiseFulfillReactions]] берётся колбэк finally и выполняется.

            если c ошибкой: из очереди [[PromiseRejectReactions]] берётся колбэк finally и выполняется.

      если с ошибкой: выполняется колбэк из catch. Колбэк создаёт промис (D). Когда:

      • выполняется промис (D):

        если успешно: из очереди [[PromiseFulfillReactions]] берётся колбэк finally и выполняется.

        если c ошибкой: из очереди [[PromiseRejectReactions]] берётся колбэк finally и выполняется.

Статические методы

У промиса есть статические методы. Их можно разделить на две группы: методы для создания промисов и методы для работы с массивами промисов.

Первая группа — методы, с помощью которых можно создать уже выполненный промис:

  • resolve создает успешно выполненный промис с переданным значением:

    snippet(24).js
    1const promise = Promise.resolve('Готово');

    Такая запись будет эквивалента:

    snippet(25).js
    1const promise = new Promise((resolve) => resolve('Готово'));

  • reject создает отклоненный промис с указанной ошибкой:

    snippet(26).js
    1const promise = Promise.reject(new Error('Ошибка доступа'));

    Такая запись будет эквивалента:

    snippet(27).js
    1const promise = new Promise((_, reject)) => reject(new Error('Ошибка доступа')));

Не путайте эти статические методы с resolve и reject внутри функции-исполнителя executor. Статические методы создают новый, уже готовый промис, а функции-аргументы управляют состоянием текущего, уже создающегося промиса.

Вторая группа — методы для работы с коллекциями промисов. На самом деле, это не обязательно должны быть промисы, но обязательно итерируемый объект. JavaScript в этом случае любезно сам обернёт значение в промис.

Все методы этой группы принимают на вход массив, а возвращают один новый промис. Состояние и результат этого промиса зависит от того, что произойдёт во время перебора всей коллекции.

Есть 4 метода:

  • Promise.all() ждёт выполнения всех переданных промисов

    Возвращаемый промис будет fulfilled когда все переданные промисы выполнятся успешно, результат —массив результатов:

    snippet(28).js
    1Promise.all([
2    Promise.resolve('Раз'),
3    Promise.resolve('Два'),
4    Promise.resolve('Три')
5  ]).then((result) => console.log(result));
    Console
    ['Раз', 'Два', 'Три']

    Возвращаемый промис будет rejected если хотя бы один переданный промис будет отклонён, результат —ошибка первого отклонённого промиса:

    snippet(29).js
    1Promise.all([
2    Promise.resolve('Раз'),
3    Promise.reject('Ой-ой, ошибочка'),
4    Promise.resolve('Три'),
5    Promise.reject('Ой-ой, снова ошибочка'),
6  ]).catch((error) => console.log(error));
    Console
    Ой-ой, ошибочка

  • Promise.race() ждёт первый завершившийся промис

    Возвращаемый промис будет fulfilled когда самый быстрый промис завершится успешно, результат — результат выполнения этого промиса:

    snippet(30).js
    1Promise.race([
2    new Promise((resolve) => setTimeout(() => resolve('Раз'), 1000)),
3    new Promise((resolve) => setTimeout(() => resolve('Два'), 5000))
4  ]).then((result) => console.log(result));
    Console
    Раз

    Возвращаемый промис будет rejected если самый быстрый промис завершился с ошибкой, результат — снова результат выполнения этого промиса:

    snippet(31).js
    1Promise.race([
2    new Promise((_, reject) => setTimeout(() => reject('Ой-ой, ошибочка'), 1000)),
3    new Promise((resolve) => setTimeout(() => resolve('Успех'), 2000)),
4    new Promise((_, reject) => setTimeout(() => reject('Ой-ой, снова ошибочка'), 3000)),
5  ]).catch((error) => console.log(error));
    Console
    Ой-ой, ошибочка

    Здесь неважно: выполнился самый быстрый промис успешно или с ошибкой — Promise.race() всегда возвращает результат или ошибку первого завершённого промиса, а результаты остальных промисов игнорируются.

  • Promise.allSettled() ждёт когда все промисы завершатся

    Возвращаемый промис будет fulfilled когда все промисы завершились: неважно — успешно или с ошибкой. Результат — массив объектов с полями в следующем формате:

    • { status: 'fulfilled', value: ... } для fulfilled промисов

    • { status: 'rejected', reason: ... } для rejected промисов

    snippet(32).js
    1Promise.allSettled([
2    Promise.resolve('Раз'),
3    Promise.reject('Ой-ой, ошибочка'),
4    Promise.resolve('Два')
5  ]).then((result) => console.log(result));
    Console
    [
    { status: 'fulfilled', value: 'Раз' },
    { status: 'rejected', reason: 'Ой-ой, ошибочка' },
    { status: 'fulfilled', value: 'Два' }
  ]

    Возвращаемый промис никогда не будет rejected, даже если все промисы будут отклонены:

    snippet(33).js
    1Promise.allSettled([
2    Promise.reject('Ой-ой, ошибочка #1'),
3    Promise.reject('Ой-ой, ошибочка #2'),
4    Promise.reject('Ой-ой, ошибочка #3'),
5  ]).then((error) => console.log(error));
    Console
    [
   { status: 'rejected', reason: 'Ой-ой, ошибочка #1' }
   { status: 'rejected', reason: 'Ой-ой, ошибочка #2' }
   { status: 'rejected', reason: 'Ой-ой, ошибочка #3' }
  ]

  • Promise.any() ждёт первый успешный, но падает если все упали

    Возвращаемый промис будет fulfilled когда самый быстрый промис завершился успешно:

    snippet(34).js
    1Promise.any([
2    Promise.reject('Ой-ой, ошибочка #1'),
3    Promise.resolve('Успех'),
4    Promise.reject('Ой-ой, ошибочка #2'),
5  ]).then((result) => console.log(result));
    Console
    Успех

    Возвращаемый промис будет rejected если все промисы завершились ошибкой. Результат — специальный объект AggregateError, у которого можно получить список ошибок:

    snippet(35).js
    1Promise.any([
2    Promise.reject('Ой-ой, ошибочка #1'),
3    Promise.reject('Ой-ой, ошибочка #2'),
4    Promise.reject('Ой-ой, ошибочка #3'),
5  ]).catch((error) => console.log(error.errors));
    Console
     [ 'Ой-ой, ошибочка #1', 'Ой-ой, ошибочка #2', 'Ой-ой, ошибочка #3' ]

Отдельно хочется отметить относительно новый метод withResolvers, добавленный в ES2024. Он делает возможным управление промисов в функции-исполнителем executor снаружи. Этот метод возвращает объект, содержащий новый промис и колбэки для управления состоянием этого промиса resolve и reject (не статические методы):

snippet(36).js
1const { promise, resolve, reject } = Promise.withResolvers();

Схлопывание и развёртывание промисов

Если передать в Promise.resolve() другой промис, то метод вернёт переданный промис без изменений. Новый промис создаваться не будет:

snippet(37).js
1const promise1 = Promise.resolve(42);
2const promise2 = Promise.resolve(promise1);
3
4console.log(promise1 === promise2);
Console
true

Этот механизм называется схлопыванием промисов.

Противоположный схлопыванию механизм происходит в then. Если колбэк внутри then возвращает новый промис, JavaScript не создаст структуру вида Promise<Promise<value>>, а дождётся разрешения внутреннего промиса и передаст его результат в следующий then. Это называется разворачиванием вложенных промисов: промисов

snippet(38).js
1Promise.resolve(1)
2  .then((value) => Promise.resolve(value + 1))
3  .then((value) => Promise.resolve(value * 2))
4  .then((value) => console.log(value));
Console
4

Что здесь происходит:

  • Promise.resolve(1) возвращает значение 1

  • Первый then в цепочке возвращает промис со значением 2

  • Второй then получает значение 2 — произошло разворачивание. Возвращает промис со значением 4

  • Третий then получает значение 4 — снова произошло разворачивание. Результат просто выводится в консоль.

Без разворачивания пришлось бы каждый раз вручную вызывать then на промисе, который вернул предыдущий колбэк:

snippet(39).js
1Promise.resolve(1)
2  .then((value) => Promise.resolve(value + 1))
3  .then((promise) => promise.then((value) => Promise.resolve(value * 2)))
4  .then((promise) => promise.then((value) => console.log(value)));

Практика: пишем свой промис

Теорию разобрали, приступаем к написанию собственного класса промиса. Опираться будем на следующий пример:

snippet(40).js
1const promise = new Promise((resolve, reject) => {
2    console.log('Бросаем монету');
3
4    setTimeout(() => {
5      const value = Math.floor(Math.random() * 2);
6
7      if (value) {
8        resolve(`Решка! Значение: ${value}`);
9      } else {
10        reject(new Error(`Орёл! Значение: ${value}`));
11      }
12    }, 1000);
13  });
14
15  promise
16    .then((result) => console.log(result))
17    .catch((error) => console.error(error.message))
18    .finally(() => console.log('Жребий брошен'));
Console
Бросаем монету
  Решка! Значение: 1 // Или выведет ошибку 'Орёл! Значение: 0'
  Жребий брошен

Что мы видим важное для нас в этом примере с первого взгляда:

  • Конструкция new Promise(...)

    Она создаёт новый объект промиса. Promise — это класс, который доступен глобально в движке JavaScript

  • Функция-исполнитель

    Функция-исполнитель запускает асинхронную операцию, которая выполнится только через какое-то время. Там в зависимости от того, какое число возвращает Math.random(), будет вызван один из двух колбэков: resolve или reject с результатом.

  • Результат обрабатывается в цепочке промисов

    Колбэки внутри then и catch просто выводят результат

  • В конце есть finally

    Просто выводит текст

Состояние и результат

Класс можно начать с написания конструктора и инициализации. У промиса всего два свойства — состояние и результат. Статусы промиса можно сразу вынести в отдельный объект:

MyPromise.js
1const STATUS = {
2    PENDING: 'pending',
3    FULFILLED: 'fulfilled',
4    REJECTED: 'rejected'
5  };

Константы защищают от опечаток. Например если писать pending вручную, можно случайно написать pendig и получить баг. С константами такого не будет, константы нам бро.

При создании промис всегда в состоянии pending, а значение неизвестно. Поэтому инициализация этих свойств будет выглядеть следующим образом:

MyPromise.js
1const STATUS = {
2  PENDING: 'pending',
3  FULFILLED: 'fulfilled',
4  REJECTED: 'rejected'
5};
6
7class MyPromise {
8  constructor(executor) {
9    this.state = STATUS.PENDING;
10    this.value = undefined;
11  }
12}

Повторение мать учения: у промисов [[PromiseResult]] хранит и результат выполнения промиса и ошибку. Это очень удобно благодаря тому, что у промиса может быть только три состояния: когда промис в состоянии pending там записано undefined, когда промис в состоянии fulfilled, там записан результат, когда в rejected — ошибка. Результат и ошибка никогда не существуют одновременно, потому что состояние меняется только один раз. Но если очень хочется, то можно всегда завести отдельное состояние для ошибки:

snippet(41).js
1const STATUS = {
2  PENDING: 'pending',
3  FULFILLED: 'fulfilled',
4  REJECTED: 'rejected'
5};
6
7class MyPromise {
8  constructor(executor) {
9    this.state = STATUS.PENDING;
10    this.value = undefined; // Для результата
11    this.error = undefined; // Для ошибки
12  }
13}

Управление состоянием промиса

Для управления состоянием промиса нужны методы resolve и reject. Их логика невероятно проста благодаря тому что состояние может меняться только один раз:

  1. Если состояние промиса не pending — ничего не делаем

  2. Если состояние промиса pending — обновляем состояние this.state: в resolve на fulfilled, в reject на rejected. Здесь же обновляем и результат выполнения промиса this.value: в resolveзаписываем результат, в reject записываем ошибку

snippet(42).js
1const resolve = (value) => {
2  if (this.state !== STATUS.PENDING) return;
3  this.state = STATUS.FULFILLED;
4  this.value = value;
5};
6
7const reject = (error) => {
8  if (this.state !== STATUS.PENDING) return;
9  this.state = STATUS.REJECTED;
10  this.value = error;
11};

Эти методы тоже добавляем в конструктор класса:

MyPromise.js
1const STATUS = {
2  PENDING: 'pending',
3  FULFILLED: 'fulfilled',
4  REJECTED: 'rejected'
5};
6
7class MyPromise {
8  constructor(executor) {
9    this.state = STATUS.PENDING;
10    this.value = undefined;
11
12    const resolve = (value) => {
13      if (this.state !== STATUS.PENDING) return;
14      this.state = STATUS.FULFILLED;
15      this.value = value;
16    };
17
18    const reject = (error) => {
19      if (this.state !== STATUS.PENDING) return;
20      this.state = STATUS.REJECTED;
21      this.value = error;
22    };
23  }
24}

Вопросик

Почему методы resolve и reject добавляются в конструктор? Если бы они были доступны снаружи, любой сторонний кусок кода мог бы вклиниться в работу промиса и принудительно завершить его, когда ему вздумается. Например:

snippet(43).js
1paymentPromise.resolve({ status: 'SUCCESS' });

В этом примере внутри paymentPromise делается запрос к банку. Если бы reject был бы доступен снаружи, злоумышленник или просто плохой код могли бы сфабриковать транзакцию. Выглядит не очень надёжно.

Поэтому resolve и reject внутри конструктора и вызвать их может только код, который находится прямо внутри функции-исполнителя. Внешний мир никак не может повлиять на исход операции.

Помимо методов resolve и reject в конструкторе должна выполняться сама функция-исполнитель. Сейчас в конструкторе ничего не проиходит. Функция-исполнитель уже передаётся в конструктор как аргумент, осталось просто запустить её. Для безопастности нужно обернуть её в try…catch:

snippet(44).js
try {
    executor(resolve, reject);
} catch (error) {
    reject(error);
}

Получаем на данном этапе следующий конструктор:

MyPromise.js
1const STATUS = {
2  PENDING: 'pending',
3  FULFILLED: 'fulfilled',
4  REJECTED: 'rejected'
5};
6

9    this.state = STATUS.PENDING;
10    this.value = undefined;
11
12    const resolve = (value) => {
13      if (this.state !== STATUS.PENDING) return;
14      this.state = STATUS.FULFILLED;
15      this.value = value;
16    };
17
18    const reject = (error) => {
19      if (this.state !== STATUS.PENDING) return;
20      this.state = STATUS.REJECTED;
21      this.value = error;
22    };
23
24    try {
25      executor(resolve, reject);
26    } catch (error) {
27      reject(error);
28    }
29  }
30}

Очереди колбэков

Также нужно добавить в конструктор два массива колбэков: [[PromiseFulfillReactions]] и [[PromiseRejectReactions]]. В них будут складываться колбэки из then и catch в том случае, если промис находится статусе pending.

При создании промиса они инициализируются как пустые списки поэтому:

MyPromise.js
class MyPromise {
  constructor(executor) {
    this.state = STATUS.PENDING;
    this.value = undefined;
    this.onFulfilledCallbacks = []; // <--- Добавили пустой массив для fulfilled-колбэков
    this.onRejectedCallbacks = []; // <--- Добавили пустой массив rejected-колбэков
    ...
  }
}

Нужно учесть эти массивы в методах resolve и reject:

  • В resolve запускаем все сохраненные колбэки из [[PromiseFulfillReactions]]

  • В reject запускаем все сохраненные колбэки из [[PromiseRejectReactions]]

snippet(45).js
const resolve = (value) => {
  if (this.state !== STATUS.PENDING) return;
  this.state = STATUS.FULFILLED;
  this.value = value;
  this.onFulfilledCallbacks.forEach(callback => callback(this.value));
};

const reject = (error) => {
  if (this.state !== STATUS.PENDING) return;
  this.state = STATUS.REJECTED;
  this.value = error;
  this.onRejectedCallbacks.forEach(callback => callback(this.value));
};

Обработка результата выполнения промиса

Методы then, catch и finally, в отличии от resolve и reject, доступны всем, кто ждёт результат промиса. Поэтому эти методы будут публичными методами класса. Также нам понадобятся статические методы resolve и reject:

snippet(47).js
1const STATUS = {
2    PENDING: 'pending',
3    FULFILLED: 'fulfilled',
4    REJECTED: 'rejected'
5  };
6
7  class MyPromise {
8    constructor(executor) {
9      ...
10    }
11
12    then(onFulfilled, onRejected) {
13      // Что-то делаем с результатом
14    }
15
16    catch(onRejected) {
17      // Что-то делаем с ошибкой
18    }
19
20    finally(onFinally) {
21      // Что-то делаем
22    }
23
24    static resolve(value) {
25    // Создать успешно выполненный промис с переданным значением
26    }
27
28    static reject(error) {
29      // Создать отклоненный промис с указанной ошибкой
30    }
31  }

Можно начать с метода catch — это просто обёртка для then с аргументами null и onRejected, поэтому:

snippet(48).js
1catch(onRejected) {
2    return this.then(null, onRejected);
3  }

А теперь займёмся методом then.

В него по спецификации JavaScript передаётся два аргумента для двух возможных исходов промиса — функции onFulfilled и onRejected для успешного выполненого и выполненного с неудачей промиса соответственно. В свою очередь у onFulfilled и onRejected один аргумент — значение с которым промис был выполнен: [[PromiseResult]] или просто this.value в нашем классе MyPromise.

По спецификации, у onFulfilled и onRejected есть поведение на случай, если вместо них были переданы не функции. Ну мало ли, всякое бывает.

  • Если onFulfilled не функция, то автоматически возвращается результат

  • Если onRejected не функция, то автоматически выбрасывается ошибка

Учтём это в методе then в самом начале во избежание дальнейших ошибок, когда будем вызывать эти функции:

snippet(49).js
then(onFulfilled, onRejected) {
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : (value) => value;
    onRejected = typeof onRejected === 'function' ? onRejected : (error) => { throw error; };
  }

Главная особенность метода then в том, что он всегда должен возвращать новый промис, на этом основана возможность строить цепочки промисов. Поэтому из метода then должнен возвращаться промис:

snippet(50).js
then(onFulfilled, onRejected) {
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : (value) => value;
    onRejected = typeof onRejected === 'function' ? onRejected : (error) => { throw error; };

    return new MyPromise((resolve, reject) => {
      // Что-то делаем с результатом
    })
  }

Важно

У возвращаемого промиса resolve и reject — это не те resolve и reject, что были в конструкторе. Это новые функции, которые управляют новым промисом — тем, который возвращает then. Они нужны для продолжения цепочки промисов.

Внутри возвращаемого промисы и будем проверить состояние текущего промиса. Промис может быть только в одном из трёх состояний, поэтому будет всего три условия:

snippet(51).js
then(onFulfilled, onRejected) {
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : (value) => value;
    onRejected = typeof onRejected === 'function' ? onRejected : (error) => { throw error; };

    return new MyPromise((resolve, reject) => {
      if (this.state === STATUS.FULFILLED) {
        // Что-то делаем с результатом
      }

      if (this.state === STATUS.REJECTED) {
        // Что-то делаем с ошибкой
      }

      if (this.state === STATUS.PENDING) {
        // Откладываем колбэки
      }
    });
  }

В зависимости от состояния промиса может выполнится одно из трёх условий:

  1. pending: откладываем колбэки в массивы onFulfilledCallbacks и onRejectedCallbacks

  2. fulfilled: вызываем onFulfilled с результатом выполнения промиса

  3. rejected: вызываем onRejected с результатом выполнения промиса (помним, что в этом случае в this.value будет записана ошибка)

Добавим вспомогательные функции handleFulfilled и handleRejected — они пригодятся для избежания повторения кода. Держа в голове список выше обновим условия:

snippet(52).js
then(onFulfilled, onRejected) {
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : (value) => value;
    onRejected = typeof onRejected === 'function' ? onRejected : (error) => { throw error; };

    return new MyPromise((resolve, reject) => {
      const handleFulfilled = () => {
        // Что-то делаем с результатом
      };

      const handleRejected = () => {
        // Что-то делаем с ошибкой
      };

      if (this.state === STATUS.FULFILLED) {
        handleFulfilled();
      }

      if (this.state === STATUS.REJECTED) {
        handleRejected();
      }

      if (this.state === STATUS.PENDING) {
        this.onFulfilledCallbacks.push(handleFulfilled);
        this.onRejectedCallbacks.push(handleRejected);
      }
    });
  }

Задержимся на условии проверки состояния pending:

snippet(53).js
if (this.state === STATUS.PENDING) {
    this.onFulfilledCallbacks.push(onFulfilled);
    this.onRejectedCallbacks.push(onRejected);
  }

У такого кода есть огромная проблема: колбэки будут вызывать синхронно, а это полностью ломает весь смысл промисов. Как это исправить? С помощью функции queueMicrotask, которая добавляет переданную функцию в очередь микрозадач:

snippet(54).js
if (this.state === STATUS.PENDING) {
    this.onFulfilledCallbacks.push(() => queueMicrotask(handleFulfilled));
    this.onRejectedCallbacks.push(() => queueMicrotask(handleRejected));
  }

Оборачивание колбэков в queueMicrotask в момент регистрации гарантирует, что даже если промис меняет статус синхронно (например сразу после создания промиса вызываем resolve со значением), колбэк выполнится после всего синхронного кода. Это точно соответствует спецификации промисов.

Аналогично нужно обернуть оставшимиеся состояния в queueMicrotask:

snippet(55).js
then(onFulfilled, onRejected) {
    onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : (value) => value;
    onRejected = typeof onRejected === 'function' ? onRejected : (error) => { throw error; };

    return new MyPromise((resolve, reject) => {
      const handleFulfilled = () => {
        // Что-то делаем с результатом
      };

      const handleRejected = () => {
        // Что-то делаем с ошибкой
      };

      if (this.state === STATUS.FULFILLED) {
        queueMicrotask(handleFulfilled);
      }

      if (this.state === STATUS.REJECTED) {
        queueMicrotask(handleRejected);
      }

      if (this.state === STATUS.PENDING) {
        this.onFulfilledCallbacks.push(() => queueMicrotask(handleFulfilled));
        this.onRejectedCallbacks.push(() => queueMicrotask(handleRejected));
      }
    });
  }

Осталось разобраться со вспомогательными функциями handleFulfilled и handleRejected.

Обе функции имеют одинаковый алгоритм:

  1. С помощью колбэка, onFulfilled или onRejected, получаем результат: значение, ошибку, undefined или промис.

  2. Если результат — промис, то нужно дождаться его выполнения

  3. Если результат не промис — вызываем resolve с этим значением

  4. Если результат ошибка — обрабатываем ошибку и вызываем reject с этим значением

В коде handleFulfilled будет выглядеть следующим образом:

snippet(56).js
const handleFulfilled = () => {
    try {
      // п.1 Получаем результат:
      const result = onFulfilled(this.value);

      if (result instanceof MyPromise) {
        // п.2 Если результат — промис, то нужно дождаться его выполнения:
        result.then(resolve, reject);
      } else {
        // п.3 Если результат не промис — вызываем resolve с этим значением
        resolve(result);
      }
    } catch (error) {
      // п.4 Если результат ошибка — обрабатываем ошибку и вызываем reject с этим значением
      reject(error);
    }
  };

Функция handleRejected похожа на handleFulfilled, но с разницей в получении результата:

snippet(57).js
1const handleRejected = () => {
2    try {
3      // п.1 Получаем результат:
4      const result = onRejected(this.value);
5
6      if (result instanceof MyPromise) {
7        // п.2 Если результат — промис, то нужно дождаться его выполнения:
8        result.then(resolve, reject);
9      } else {
10        // п.3 Если результат не промис — вызываем resolve с этим значением
11        resolve(result);
12      }
13    } catch (error) {
14      // п.4 Если результат ошибка — обрабатываем ошибку и вызываем reject с этим значением
15      reject(error);
16    }
17  };

Может показаться, что на (11) строчке затесалась ошибка и вместо resolve(result) должно быть reject(result), но это не так, всё написано верно. Давайте проведём небольшой эксперимент. Что выведет код ниже?

snippet(58).js
Promise.reject('Ошибка')
    .catch(() => {
      return 'Всё хорошо';
    })
    .then((result) => console.log(result));
Console
Всё хорошо

А здесь?

snippet(59).js
Promise.reject('Ошибка 1')
    .catch(() => {
      throw new Error('Ошибка 2');
    })
    .catch((error) => console.log(error.message));
Console
Ошибка 2

В первом примере изначальный промис выполняется с ошибкой «Ошибка», эту ошибку ловит catch, но из самого catch возвращается не ошибка, а обычное значение «Всё хорошо». Во втором примере изначальный промис тоже выполняется с ошибкой, эту ошибку ловит catch, но в этот раз из самого catch возвращается другая ошибка.

Такое поведение можно назвать восстановлением после ошибки: если в цепочке выбрасывается ошибка — цепочка останется rejected, но если вернуть из цепочки обычное значение, то состояние цепочки меняется с rejected на fulfilled или другими словами восстанавливается. Собственно, в строчке (11) это и происходит — восстановление цепочки. При этом не следует путать: это меняется не состояние изначального промиса — он как был rejected так и остался rejected. Из каждого then или catch возвращается новый промис с новым состоянием.

Осталось написать метод finally.

Что нам о нём известно:

  • Выполняется в любом случае

    Если промис fulfilled и если промис rejected

  • Не меняет состояние промиса

    Если промис был fulfilled — промис останется fulfilled, если был rejected — останется rejected

  • Не меняет значение промиса

    А передаёт его дальше (если есть методы дальше в цепочке). Если вернуть значение — оно будет проигнорировано

  • Из finally можно выбросить ошибку

    Если вернуть значение, то оно будет проигнорировано

  • Это синтаксический сахар над then

    Не нужно писать всю логику с нуля, надо воспользоваться then

Воспользуемся методом then, написанным ранее. У метода есть два аргумента — колбэки onFulfilled (c аргументом value) и onRejected (с аргументом error). В обоих колбэках нам необходимо выполнить onFinally, значение пробросить дальше, а ошибку выбросить:

snippet(60).js
finally(onFinally) {
      return this.then(
        (value) => {
          // Выполнить onFinally и пробросить value дальше
        },
        (error) => {
          // Выполнить onFinally и выбросить error
        }
      );
    }

Первый вариант, который приходит в голову:

snippet(61).js
finally(onFinally) {
    return this.then(
      (value) => {
        onFinally();
        return value;
      },
      (error) => {
        onFinally();
        throw error;
      }
    );
  }

Выглядит отлично, все условия выполняются: выполняем onFinally, значение передаём дальше, ошибку выбрасываем. Но у этой этой реализации есть проблема. Пример, где всё сломается:

snippet(62).js
const promise = new MyPromise((resolve, reject) => {
    resolve(42);
  });

  promise
    .finally(() => new MyPromise((resolve) => setTimeout(resolve, 10000)))
    .then((result) => console.log('Результат:', result))
    .catch((error) => console.error('Ошибка:', error.message));

В консоли выведется «Результат: 42», но важно здесь не то, что выведется, а когда. Промис с задержкой от таймера в 10000 ms был проигнорирован! Результатом выполнения промиса может быть что угодно: число, строку, undefined и промис. Здесь про промисы вообще забыли. Хоть finally и пробрасывает исходное значение дальше, но промисы все всегда обязаны ждать.

Чтобы это исправить воспользуемся лайфхаком: если передать в Promise.resolve() другой промис, то метод вернет этот же самый переданный промис без изменений, новый объект создаваться не будет:

snippet(63).js
const promise1 = Promise.resolve(42);
const promise2 = Promise.resolve(promise1);

console.log(promise1 === promise2);

Внутри движок JavaScript проверяет тип аргумента и если это промис, то он возвращается как есть, полностью сохраняя состояние и значение, будь они хоть fulfilled с результатом или rejected с ошибкой.

У нас этот механизм пока не реализован. Добавим для этого два статических метода в класс — resolve и reject:

snippet.js
1static resolve(value) {
2  // Что-то сделать
3}
4
5static reject(error) {
6  // Что-то сделать
7}

Они буду отличаться от своих тёзок в конструкторе:

  • resolve и reject как методы в конструкторе

    Работают только внутри функции-исполнителя executor и меняют состояние только текущего промиса

  • resolve и reject как статические методы

    Создают новый промис и могут быть вызваны где угодно в коде. Это как Math.random() — Math тоже класс, а random — его статический метод.

Что должны делать эти статические методы? Мы уже отвечали на этот вопрос, например, когда писали handleFulfilled или handleRejected. Только здесь задача будет ещё проще:

  • Если значение уже промис — возвращаем его как есть

  • Если значение обычное значение — создаём новый промис, которому сразу вызываем resolve(value)

  • Если ошибка — создаём промис, которому сразу вызываем reject(error)

snippet(64).js
1static resolve(value) {
2  if (value instanceof MyPromise) return value;
3  return new MyPromise((resolve) => resolve(value));
4}
5
6static reject(error) {
7  return new MyPromise((_, reject) => reject(error));
8}

Проверим:

snippet(65).js
1const promise1 = MyPromise.resolve(42);
2const promise2 = MyPromise.resolve(promise1);
3
4console.log(promise1 === promise2); // true

Теперь надо подправить finally. Добавляем возврат промиса из обоих колбэков:

snippet(66).js

2    return this.then(
3      (value) => {
4        return MyPromise.resolve(x);
5      },
6      (error) => {
7        return MyPromise.resolve(x);
8      }

Теперь у нас есть защита на все случаи: если вернётся обычное значение, если вернётся ошибка, если вернётся промис — мы готовы ко всему. Осталось понять, что написать внутри.

Но теперь нельзя просто так написать внутри промиса:

В созданный статическим методом промис сейчас передаётся функция, а не результат её вызова. onFinally никогда не вызывается, value не возвращается, error никогда не выбрасывается.

Нам нужно:

  1. Вызвать onFinally, получить результат:

    snippet(68).js
    1const result = onFinally();

  2. Передать result в статический метод resolve:

    snippet(69).js
    1MyPromise.resolve(result)

    Это тот промис, который потом будем возвращать из каждого колбэка then.

  3. Так как это промис, то мы можем вызвать у него then и продолжить цепочку. В случае с fulfilled значение просто передаётся дальше:

    snippet(70).js
    1return MyPromise.resolve(result).then(() => value);

    А в случае ошибки выбрасывается ошибка:

    snippet(71).js
    1return MyPromise.resolve(result).then(() => { throw error; });

2    PENDING: "pending",
3    FULFILLED: "fulfilled",
4    REJECTED: "rejected",
5  };
6  
7  class MyPromise {
8    constructor(executor) {
9      this.state = STATUS.PENDING;
10      this.value = undefined;
11      this.onFulfilledCallbacks = [];
12      this.onRejectedCallbacks = [];
13  
14      const resolve = (value) => {
15        if (this.state !== STATUS.PENDING) return;
16        this.state = STATUS.FULFILLED;
17        this.value = value;
18

20      };
21  
22      const reject = (error) => {
23        if (this.state !== STATUS.PENDING) return;

25        this.value = error;
26

28      };
29

32      } catch (error) {

34      }
